Block 1 · Data Science in security

From SIEMs to data analysis

Twenty years ago, “security and data” meant a SIEM: a single product that collected everything and told you where to look.

A SIEM does six things: it aggregates data from many sources, correlates it, raises alerts, analyses behaviour, draws dashboards and produces compliance reports.

That is good and still necessary. But it only answers the questions somebody programmed into it. When the question is new, or it is yours, it is time for data analysis.

The analytics ladder
Describe what happened → understand why → predict what will happen → decide what to do. Each step asks for more data, more care and more questions.
Block 1 · Data Science

Doing data science is not doing magic

A nuance worth having clear from day one.

@kwbroman
Karl Broman's point, paraphrased: physicists who do mathematics do not call it “number science”; it is simply maths. In the same way, analysing data is doing statistics, whatever label goes on it: data science, informatics or analytics.
  • No magic formula is needed: you need method, and the ability to tell a figure from a piece of evidence.
  • What is new is the scale (millions of rows), the tool (code, not spreadsheets) and the context (security, where a wrong figure has consequences).
Block 1 · The four phases

Question, data, analysis, communication

A data analysis in security is always this journey. Measurable at the end: being able to name the four.

01
The question is what matters
Before touching anything: what do I want to know, and what will I do with the answer? “How many vulnerabilities are there?” is a poor question; “which weaknesses recur most, and why?” is a different one.
02
The data
Where it comes from, who maintains it, how old it is, what it does not say. Without that there is no analysis, only arithmetic.
03
The analysis
Clean, explore, summarise, model. This is where statistics and machine learning live (S4).
04
The communication
A chart, a table, a report that somebody else can read, challenge and regenerate (S2).
Block 2 · Where the data comes from

Three families of security data

They differ in what they are, in who owns them and in how they can be compared.

FamilyExamplesWho holds itComparable?
Logs and telemetryServer, firewall, EDR and SIEM recordsEach organisationHard: every product describes things differently
InventoriesInstalled software, assets, configurationsEach organisationHard: names are free text
StandardsCVE, CPE, CWE, CAPEC, ATT&CKA body that maintains and publishes themYes: that is why they exist
We apply analysis to logs and inventories; we anchor what we find to the standards, so that we are all talking about the same thing. That is what this course is about.

Block 3 · git (1 of 2)

What git is, and what you can skip today

A version control system: it keeps every change, who made it and when. Today you only learn what you need to submit your work.

Three places where your files live:

  • The working directory: the folder you see in the file explorer.
  • The local repository: the history, in the hidden .git folder on your computer.
  • The remote repository: the copy on GitHub.

Between the working directory and the repository sits the staging area (staging): choosing which changes go into the next commit.

Out of scope today
Branches, merge, rebase, HEAD, conflicts. You will meet them when you need them; today's exercise does not.
Block 3 · git (2 of 2)

The cycle: clone, add, commit, push

20 minutes, with a live demo. Then you do it yourselves in the exercise.

  1. git cloneDownloads the repository from GitHub to your computer. Done only once.
  2. git addMarks the file that changed: it enters the staging area.
  3. git commit -m "…"Saves the staged changes to the local history, with a message.
  4. git pushSends the commits to GitHub.
What you should see
  • git status: what has changed and what is staged.
  • git log --oneline: the history.
  • On GitHub, the file and the commit you have just made.
  • A message that says what: “Exercise 0: first query”, not “changes”.

Only what Exercise 0 needs

What went wrong, and what “standardised” means

First, the environment problems: better today than in S2. Then a question about the table you have just counted.

01
What failed for you?Environment
The mitre version (CRAN versus dds-2026), GitHub authentication, lubridate not installed. Every incident goes into the guide.
02
Look at the yearsSample?
There are very few CVEs before 2017 (2015: 101; 2017: about 18,000) and 2025 stops in April. What does the table say, and what does it not say?
03
Three CVEs with no dateGaps
A “standard” column has holes too. Having an identifier does not mean having all the data.
04
What does it mean for data to be “standardised”?Definition
That it has an identifier, a definition, a maintainer and a version: CVE-2021-44228 means the same thing to everybody. It does not mean it is complete or correct.
Compliance block · 10 min

Before we close

Who does security data belong to?

Concept
A CVE is public: anyone can look at it, cite it and compare it. An inventory of the software on a laptop is not: it says what you installed, when and in which versions. The same kind of data, two different answers.
Rule
Students' data does not leave your laptop. The course repository already provides for it: the .gitignore excludes *.json and outputs/.
Link
In S3 we will build an inventory of your software. From today you should be able to say which of the two cases a piece of data is before you push it.
